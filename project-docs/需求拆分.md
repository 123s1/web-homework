# 省博物馆参观预约系统需求拆分

## 1. 文档目的

本文档根据 `项目要求分析.md` 对省博物馆参观预约系统进行需求拆分，明确系统需要实现的用户角色、功能模块、业务规则、非功能要求、优先级、验收标准以及当前需求中仍需补充确认的内容。

本文档用于指导后续：

- **数据库设计**
- **后端接口设计**
- **前端页面设计**
- **功能开发顺序安排**
- **功能测试用例编写**
- **系统设计文档整理**

---

## 2. 项目总体需求

本项目需要实现一个完整的 **省博物馆参观预约系统**。

系统核心目标是：

```text
游客可以实名登录并预约参观时段；
管理员可以配置场馆信息、预约活动、时段名额和预约规则；
系统在高并发预约场景下必须保证不超额、不重复、名额数据准确一致；
系统最终可以部署到 VMware Linux 虚拟机，并由宿主机浏览器正常访问。
```

项目采用前后端分离架构：

```text
Vue 前端
    ↓ Axios 请求
Spring Boot 后端 REST API
    ↓ 操作数据库
MySQL 数据库
```

## 3. 用户角色拆分

系统主要包含两个角色：

### 3.1 游客用户

游客是预约系统的普通使用者。

主要操作包括：

- **实名登录**
- **浏览场馆信息**
- **查看通知公告**
- **查看可预约日期和时段**
- **提交预约**
- **查看预约结果**
- **查看我的预约记录**
- **查看预约凭证和二维码**

### 3.2 管理员用户

管理员是预约系统的后台管理者。

主要操作包括：

- **登录后台系统**
- **维护场馆开放信息**
- **维护参观须知**
- **发布通知公告**
- **配置预约活动**
- **配置每日总名额**
- **配置分时时段名额**
- **设置单人预约上限**
- **设置预约开放时间和结束时间**
- **启用或禁用预约通道**
- **查看预约记录**
- **导出预约名单**
- **查看预约统计和系统状态**

## 4. 游客端功能需求拆分

### 4.1 游客实名登录

#### 4.1.1 功能说明

游客使用身份证号和手机号进行实名登录。

#### 4.1.2 输入内容

- **姓名，可选或必填均可，建议保留**
- **身份证号**
- **手机号**

#### 4.1.3 业务规则

- **身份证号必须为 18 位**
- **手机号必须为 11 位大陆手机号格式**
- **如果游客不存在，则自动创建游客信息**
- **如果游客已存在，则更新手机号或姓名信息**

#### 4.1.4 输出结果

- **登录成功**
- **身份证号格式错误**
- **手机号格式错误**

#### 4.1.5 优先级

高。

这是游客预约流程的入口。

---

### 4.2 场馆信息浏览

#### 4.2.1 功能说明

游客可以查看博物馆基本信息、开放时间、参观须知和预约规则。

#### 4.2.2 展示内容

- **场馆名称**
- **场馆地址**
- **开放时间说明**
- **参观须知**
- **预约规则**
- **更新时间**

#### 4.2.3 业务规则

- **场馆信息由管理员后台维护**
- **游客端只负责展示，不允许修改**

#### 4.2.4 优先级

高。

作业要求用户端能够查看场馆开放信息和参观规则。

---

### 4.3 通知公告浏览

#### 4.3.1 功能说明

游客可以查看博物馆发布的通知公告，例如特殊展览、临时闭馆等。

#### 4.3.2 展示内容

- **公告标题**
- **公告内容**
- **公告类型**
- **发布时间**
- **是否启用**

#### 4.3.3 业务规则

- **只展示已启用公告**
- **按发布时间倒序显示**
- **公告由管理员后台维护**

#### 4.3.4 优先级

中。

属于信息浏览功能，建议实现。

---

### 4.4 可预约时段查询

#### 4.4.1 功能说明

游客可以查看可预约日期、入场时段、总名额、已预约人数和剩余名额。

#### 4.4.2 展示内容

- **参观日期**
- **入场时段名称**
- **入场开始时间**
- **入场结束时间**
- **总名额**
- **已预约人数**
- **剩余名额**
- **预约开始时间**
- **预约结束时间**
- **预约通道状态**

#### 4.4.3 业务规则

- **只展示有效预约活动下的时段**
- **剩余名额 = 总名额 - 已预约人数**
- **前端可以根据剩余名额控制按钮状态，但不能依赖前端防超额**

#### 4.4.4 优先级

高。

这是预约流程的核心前置功能。

---

### 4.5 提交预约

#### 4.5.1 功能说明

游客选择参观日期和入场时段后，提交预约请求。

#### 4.5.2 输入内容

- **游客身份证号**
- **游客手机号**
- **预约时段 ID**

#### 4.5.3 后端校验规则

提交预约时，后端必须完成以下校验：

```text
1. 身份证号格式校验
2. 手机号格式校验
3. 预约时段是否存在
4. 预约活动是否有效
5. 预约通道是否启用
6. 当前时间是否早于预约开始时间
7. 当前时间是否晚于预约结束时间
8. 当前时段是否还有剩余名额
9. 当前游客是否重复预约
10. 当前游客是否超过预约上限
11. 名额扣减是否成功
12. 预约记录是否写入成功
```

#### 4.5.4 输出结果

必须覆盖以下结果：

- **预约成功**
- **名额已满**
- **已超过预约上限**
- **未到预约时间**
- **预约已结束**
- **预约通道已关闭**
- **重复预约失败**
- **身份证号或手机号格式错误**
- **系统异常，请稍后重试**

#### 4.5.5 数据一致性要求

必须保证：

- **不能超额预约**
- **不能重复预约**
- **预约记录数量与已预约名额一致**
- **并发情况下成功人数不能超过设置名额**

#### 4.5.6 优先级

最高。

该功能直接对应评分中的功能完整性、数据一致性和高并发稳定性。

#### 4.6.2 查询条件

#### 4.6.3 展示内容

#### 4.6.4 业务规则

### 4.7 预约凭证与二维码

#### 4.7.1 功能说明

游客预约成功后，系统生成预约凭证和二维码。

#### 4.7.2 凭证内容

- **预约编号**

## 6. 核心业务规则拆分

### 6.1 时间规则

系统必须严格控制预约时间。

规则包括：

- **未到预约开始时间不能预约**
- **超过预约结束时间不能预约**
- **活动状态为已结束不能预约**
- **预约通道关闭不能预约**
- **时段禁用不能预约**

### 6.2 名额规则

系统必须严格控制名额。

规则包括：

- **每个时段有独立总名额**
- **已预约人数不能超过总名额**
- **剩余名额 = 总名额 - 已预约人数**
- **并发预约时不能出现超额预约**
- **后台调整名额时不能低于已预约人数**

### 6.3 重复预约规则

系统必须防止重复预约。

建议规则：

```text
同一身份证号同一天只能预约一次。
```

也可以根据作业要求扩展为：

```text
同一身份证号同一活动只能预约一次。
```

### 6.4 单人预约上限规则

管理员可以设置单人预约上限。

建议规则：

- **单人每天最多预约 1 次，默认规则**
- **如果后台配置了更高上限，则按后台配置执行**
- **超过上限时返回“已超过预约上限”**

### 6.5 数据一致性规则

必须保证：

- **预约记录插入成功后，名额必须同步变化**
- **名额扣减失败时，不能产生成功预约记录**
- **预约成功记录数应与 booked_count 一致**
- **并发请求下成功数量不能超过总名额**

### 6.6 并发控制规则

推荐采用：

```text
事务控制 + 数据库条件更新 + 唯一约束
```

核心思路：

```sql
UPDATE reservation_slot
SET booked_count = booked_count + 1,
    version = version + 1
WHERE id = ?
  AND enabled = 1
  AND booked_count < total_capacity;
```

并通过唯一约束防重复：

```text
id_card + visit_date
```

## 7. 非功能需求拆分

### 7.1 高并发与稳定性

系统需要支持大量用户同时预约。

要求：

- **预约接口高并发下不崩溃**
- **请求能正常返回成功或失败结果**
- **不能因为并发导致数据库错误**
- **不能出现页面长时间卡死**

验收方式：

- **使用 JMeter、Apifox、Postman Runner 或脚本压测**
- **记录并发数、请求数、成功数、失败数、响应时间**

### 7.2 数据一致性

这是本项目最重要的非功能需求。

必须保证：

- **无超额预约**
- **无重复预约**
- **名额数据精准一致**

验收方式：

```text
设置某个时段名额为 10，同时发送 100 个预约请求。
最终成功数量不能超过 10，booked_count 必须等于成功预约记录数。
```

### 7.3 可部署性

系统必须部署到 VMware Linux 虚拟机。

要求：

- **VMware 固定 8GB 内存**
- **Linux 系统正常运行**
- **JDK 安装成功**
- **MySQL 安装成功**
- **项目 jar 可以启动**
- **宿主机浏览器可以访问系统**

### 7.4 易用性

系统页面应保证基本可用。

要求：

- **游客能清楚看到预约状态和剩余名额**
- **预约失败原因要明确显示**
- **后台配置入口清晰**
- **表单校验提示清楚**

### 7.5 可测试性

系统应便于测试和截图。

要求：

- **关键功能都有明确页面入口**
- **预约成功和失败场景可复现**
- **后台可查看数据核对结果**
- **压测后可查看数据库一致性结果**

## 8. 需求优先级划分

### 8.1 P0 必须完成

P0 是影响主要评分和系统闭环的功能。

必须完成：

- **游客实名登录**
- **场馆信息展示**
- **可预约时段展示**
- **核心预约接口**

## 14. 我认为还需要补充确认的地方

### 14.1 管理员登录方式

需要确认后台登录采用哪种方式。

建议大作业阶段采用简单方案：

```text
管理员用户名 + 密码登录，前端保存简单 token 或登录状态。
```

不建议一开始引入复杂 Spring Security，否则配置和调试成本较高。

### 14.2 单人预约上限的精确定义

作业提到单人预约上限和单日可预约次数，但没有明确具体规则。

建议定义为：

```text
同一身份证同一天最多预约一次。
```

如果后台设置 `person_limit > 1`，则允许同一身份证同一天最多预约对应次数，但不能重复预约同一时段。

### 14.3 二维码真实程度

作业要求查看入园二维码，但没有要求扫码核销。

建议实现为：

```text
预约成功后，根据预约编号生成二维码。
```

不做扫码核验功能，除非后续时间充足。

### 14.4 在线预约请求量如何实现

作业提到查看当前在线预约请求量，但完整实时在线统计实现较复杂。

建议简化为：

```text
统计预约接口累计请求数、最近请求时间、成功预约数、失败预约数。
```

这样更容易演示和写入系统状态页面。

### 14.5 导出格式

作业只要求导出预约名单，没有限定格式。

建议优先使用：

```text
CSV 导出
```

如果时间充足，再扩展 Excel 导出。

### 14.6 前端路由复杂度

如果你对 Vue 不熟，不建议一开始引入复杂路由和状态管理。

建议先用简单页面切换方式完成作业功能，后续再根据需要引入 Vue Router。

### 14.7 并发测试工具

需要提前选择性能测试工具。

建议优先选择：

```text
JMeter
```

如果安装和配置麻烦，可以先使用脚本压测辅助验证，再整理成性能测试报告。
