## 2. 数据库设计目标

数据库需要支撑游客端、管理员端和核心预约流程。

总体目标如下：

```text
游客实名登录后，可以查看场馆信息、公告、预约日期和分时时段，并提交预约；
管理员可以维护场馆信息、公告、预约活动、分时时段名额，并查看预约记录和统计数据；
系统在多个游客同时预约同一时段时，不能出现超额预约、重复预约或名额数据不一致。
```

数据库重点解决的问题：

- **用户身份**：保存游客实名信息和管理员账号。
- **场馆展示**：保存场馆信息、开放时间、参观须知和公告。
- **预约配置**：保存可预约日期、预约开放时间、预约结束时间、单人预约上限和分时时段名额。
- **预约记录**：保存预约编号、游客信息、参观日期、时段和二维码凭证内容。
- **并发安全**：通过数据库条件更新、唯一约束和事务控制防止超额和重复预约。
- **统计查询**：支持后台统计总名额、已预约人数、剩余名额和分时段预约人数。

## 3. 数据库基础约定

### 3.1 数据库类型

正式系统使用：

```text
MySQL 8.0
```

推荐配置如下：

| 配置项 | 推荐值 |
| --- | --- |
| 存储引擎 | InnoDB |
| 字符集 | utf8mb4 |
| 排序规则 | utf8mb4_unicode_ci |
| 主键类型 | BIGINT UNSIGNED AUTO_INCREMENT |
| 时间字段 | DATETIME |

选择 InnoDB 的原因：

- **支持事务**
- **支持行级锁**
- **支持外键约束**
- **适合预约名额这种强一致性业务**

### 3.2 命名规范

| 类型 | 规范 | 示例 |
| --- | --- | --- |
| 数据库名 | 小写英文 + 下划线 | `museum_reservation` |
| 表名 | 小写英文 + 下划线 | `reservation_record` |
| 字段名 | 小写英文 + 下划线 | `booked_count` |
| 主键名 | 统一使用 `id` | `id` |
| 创建时间 | 统一使用 `created_at` | `created_at` |
| 更新时间 | 统一使用 `updated_at` | `updated_at` |

### 3.3 时间字段约定

| 字段 | 说明 |
| --- | --- |
| `created_at` | 数据创建时间 |
| `updated_at` | 数据最后更新时间 |
| `booking_start` | 预约开放开始时间 |
| `booking_end` | 预约开放结束时间 |
| `visit_date` | 参观日期 |
| `start_time` | 入场时段开始时间 |
| `end_time` | 入场时段结束时间 |

时间规则：

- **`booking_end` 必须晚于 `booking_start`**
- **`end_time` 必须晚于 `start_time`**
- **预约开放判断必须以后端服务器时间为准**
- **前端时间显示只能作为提示，不能作为最终校验依据**

### 3.4 状态值约定

#### 3.4.1 通用启用状态

| 值 | 含义 |
| --- | --- |
| `1` | 启用 |
| `0` | 禁用 |

#### 3.4.2 公告类型

| 值 | 含义 |
| --- | --- |
| `NORMAL` | 普通通知 |
| `EXHIBITION` | 特殊展览 |
| `CLOSE` | 闭馆通知 |
| `RULE` | 预约规则 |

#### 3.4.3 预约活动状态

| 值 | 含义 |
| --- | --- |
| `DRAFT` | 草稿，暂不开放 |
| `OPEN` | 启用，游客端可按时间规则预约 |
| `CLOSED` | 已关闭，不允许预约 |
| `DISABLED` | 禁用，不允许预约 |

说明：

```text
活动是否未开始或已结束主要由当前时间与 booking_start、booking_end 对比得出；
status 主要表示管理员是否手动启用该预约活动。
```

#### 3.4.4 预约记录状态

| 值 | 含义 |
| --- | --- |
| `SUCCESS` | 预约成功 |
| `CANCELLED` | 已取消，预留状态 |

课程大作业初期可以只实现 `SUCCESS`，不实现取消功能。

## 5. 表关系设计

### 5.1 关系总览

```text
admin_user
    独立表，用于后台登录

museum_info
    独立表，用于游客端和后台展示场馆信息

notice
    独立表，用于公告管理

visitor 1 ─── N reservation_record
    一个游客可以有多条预约记录

reservation_activity 1 ─── N reservation_slot
    一个预约活动可以包含多个分时时段

reservation_activity 1 ─── N reservation_record
    一个预约活动可以产生多条预约记录

reservation_slot 1 ─── N reservation_record
    一个预约时段可以产生多条预约记录

request_log
    独立表，用于记录请求统计，可选
```

### 5.2 核心预约链路关系

核心预约链路依赖以下表：

```text
visitor
reservation_activity
reservation_slot
reservation_record
```

提交预约时的数据流如下：

```text
1. 根据身份证号找到或创建 visitor。
2. 根据 slot_id 找到 reservation_slot。
3. 根据 activity_id 找到 reservation_activity。
4. 校验预约活动状态、预约时间、时段状态和剩余名额。
5. 原子更新 reservation_slot.booked_count。
6. 插入 reservation_record。
7. 返回预约编号和二维码内容。
```

## 6. 详细表结构设计

### 6.1 管理员表 admin_user

#### 6.1.1 表作用

`admin_user` 用于保存后台管理员账号信息，支撑管理员登录和后台权限判断。

#### 6.1.2 字段设计

| 字段名 | 类型 | 是否为空 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | BIGINT UNSIGNED | 否 | 自增 | 主键 |
| `username` | VARCHAR(50) | 否 | 无 | 管理员用户名 |
| `password` | VARCHAR(100) | 否 | 无 | 管理员密码，后续可存储加密值 |
| `role` | VARCHAR(30) | 否 | `ADMIN` | 管理员角色 |
| `status` | TINYINT | 否 | `1` | 状态，1 启用，0 禁用 |
| `created_at` | DATETIME | 否 | 当前时间 | 创建时间 |
| `updated_at` | DATETIME | 否 | 当前时间 | 更新时间 |

#### 6.1.3 约束与索引

| 类型 | 字段 | 说明 |
| --- | --- | --- |
| 主键 | `id` | 唯一标识管理员 |
| 唯一索引 | `username` | 防止管理员用户名重复 |
| 普通索引 | `status` | 便于查询启用管理员 |

#### 6.1.4 设计说明

- **系统初始化时预置一个管理员账号。**
- **大作业阶段可使用简单登录逻辑，不强制引入 Spring Security。**
- **如果时间允许，密码可改为加密存储。**

### 6.2 游客表 visitor

#### 6.2.1 表作用

`visitor` 用于保存游客实名信息。游客登录和预约记录都依赖该表。

#### 6.2.2 字段设计

| 字段名 | 类型 | 是否为空 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | BIGINT UNSIGNED | 否 | 自增 | 主键 |
| `name` | VARCHAR(50) | 否 | 无 | 游客姓名 |
| `id_card` | VARCHAR(18) | 否 | 无 | 身份证号 |
| `phone` | VARCHAR(20) | 否 | 无 | 手机号 |
| `created_at` | DATETIME | 否 | 当前时间 | 创建时间 |
| `updated_at` | DATETIME | 否 | 当前时间 | 更新时间 |

#### 6.2.3 约束与索引

| 类型 | 字段 | 说明 |
| --- | --- | --- |
| 主键 | `id` | 唯一标识游客 |
| 唯一索引 | `id_card` | 一个身份证号对应一个游客 |
| 普通索引 | `phone` | 支持按手机号查询 |

#### 6.2.4 设计说明

- **身份证号是游客实名身份的核心标识。**
- **游客首次登录时，如果身份证号不存在，则创建游客记录。**
- **游客再次登录时，如果手机号或姓名发生变化，可更新 `name` 和 `phone`。**
- **身份证号和手机号格式主要由后端校验，数据库通过长度和非空约束辅助保证。**

### 6.5 预约活动表 reservation_activity

#### 6.5.1 表作用

`reservation_activity` 用于配置某一天的预约规则，包括参观日期、每日总名额、预约开放时间、预约结束时间、单人预约上限和活动状态。

#### 6.5.2 字段设计

| 字段名 | 类型 | 是否为空 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | BIGINT UNSIGNED | 否 | 自增 | 主键 |
| `activity_name` | VARCHAR(100) | 否 | 无 | 预约活动名称 |
| `visit_date` | DATE | 否 | 无 | 参观日期 |
| `daily_capacity` | INT UNSIGNED | 否 | 无 | 当日预约总名额上限 |
| `person_limit` | INT UNSIGNED | 否 | `1` | 单人预约上限 |
| `booking_start` | DATETIME | 否 | 无 | 预约开放开始时间 |
| `booking_end` | DATETIME | 否 | 无 | 预约开放结束时间 |
| `status` | VARCHAR(20) | 否 | `DRAFT` | 活动状态 |
| `created_at` | DATETIME | 否 | 当前时间 | 创建时间 |
| `updated_at` | DATETIME | 否 | 当前时间 | 更新时间 |

#### 6.5.3 约束与索引

| 类型 | 字段 | 说明 |
| --- | --- | --- |
| 主键 | `id` | 唯一标识预约活动 |
| 唯一索引 | `visit_date` | 简化设计：同一参观日期只允许一个预约活动 |
| 普通索引 | `status` | 查询启用或关闭活动 |
| 普通索引 | `booking_start`, `booking_end` | 按预约时间范围查询 |

#### 6.5.4 业务约束

必须满足：

```text
booking_end > booking_start
daily_capacity > 0
person_limit > 0
```

时段容量约束：

```text
同一预约活动下，所有启用时段的 total_capacity 总和不应超过 reservation_activity.daily_capacity。
```

#### 6.5.5 设计说明

- **预约活动控制某一天是否开放预约。**
- **游客是否能预约，需要同时满足活动状态、预约时间和时段状态。**
- **`daily_capacity` 是每日总上限，具体时段名额在 `reservation_slot` 中配置。**
- **为降低大作业实现复杂度，正式系统初期采用“一天一个预约活动”的设计。**

### 6.6 预约时段表 reservation_slot

#### 6.6.1 表作用

`reservation_slot` 是数据库中最关键的表之一，用于保存某个预约活动下的分时时段、时段总名额、已预约人数和并发控制版本号。

该表直接影响：

- **剩余名额展示**
- **是否允许预约**
- **高并发下是否超额**
- **预约统计是否准确**

#### 6.6.2 字段设计

| 字段名 | 类型 | 是否为空 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | BIGINT UNSIGNED | 否 | 自增 | 主键 |
| `activity_id` | BIGINT UNSIGNED | 否 | 无 | 所属预约活动 ID |
| `visit_date` | DATE | 否 | 无 | 参观日期，冗余保存便于查询 |
| `slot_name` | VARCHAR(50) | 否 | 无 | 时段名称，例如 09:00-11:00 |
| `start_time` | TIME | 否 | 无 | 入场开始时间 |
| `end_time` | TIME | 否 | 无 | 入场结束时间 |
| `total_capacity` | INT UNSIGNED | 否 | 无 | 时段总名额 |
| `booked_count` | INT UNSIGNED | 否 | `0` | 已预约人数 |
| `enabled` | TINYINT | 否 | `1` | 是否启用，1 启用，0 禁用 |
| `version` | INT UNSIGNED | 否 | `0` | 版本号，用于并发控制 |
| `created_at` | DATETIME | 否 | 当前时间 | 创建时间 |
| `updated_at` | DATETIME | 否 | 当前时间 | 更新时间 |

#### 6.6.3 约束与索引

| 类型 | 字段 | 说明 |
| --- | --- | --- |
| 主键 | `id` | 唯一标识预约时段 |
| 外键 | `activity_id` | 关联 `reservation_activity.id` |
| 唯一索引 | `activity_id`, `start_time`, `end_time` | 防止同一活动下重复配置相同时段 |
| 普通索引 | `activity_id` | 查询活动下所有时段 |
| 普通索引 | `visit_date`, `enabled` | 游客端按日期查询可预约时段 |

#### 6.6.4 业务约束

必须满足：

```text
end_time > start_time
total_capacity > 0
booked_count >= 0
booked_count <= total_capacity
```

后台调整名额时必须满足：

```text
新的 total_capacity >= 当前 booked_count
```

剩余名额计算：

```text
remaining = total_capacity - booked_count
```

#### 6.6.5 设计说明

- **`booked_count` 是预约成功人数的快速统计字段。**
- **预约成功时，必须先通过数据库条件更新增加 `booked_count`，再插入预约记录。**
- **`version` 可用于乐观锁或辅助记录并发更新次数。**
- **游客端显示剩余名额时，可以由 `total_capacity - booked_count` 得出。**

## 8. 并发预约与数据一致性设计

### 8.1 核心风险

预约系统最大风险是多个游客同时抢同一个时段名额。

错误实现方式如下：

```text
1. 先查询剩余名额。
2. 如果剩余名额大于 0，则继续预约。
3. 普通更新 booked_count。
```

该方式在高并发下可能导致多个请求同时看到同一个剩余名额，从而出现超额预约。

### 8.2 推荐实现方式

本系统推荐使用：

```text
数据库条件更新 + 唯一约束 + 事务控制
```

核心条件更新语句：

```sql
UPDATE reservation_slot
SET booked_count = booked_count + 1,
    version = version + 1
WHERE id = ?
  AND enabled = 1
  AND booked_count < total_capacity;
```

判断方式：

```text
影响行数 = 1：名额扣减成功，可以继续插入预约记录。
影响行数 = 0：名额已满或时段不可预约，返回预约失败。
```

### 8.3 事务边界

提交预约接口必须放入同一个数据库事务。

事务内步骤：

```text
1. 校验身份证号和手机号格式。
2. 查询或创建 visitor。
3. 查询 reservation_slot 和 reservation_activity。
4. 校验活动状态、预约时间、时段状态。
5. 校验是否重复预约和是否超过单人上限。
6. 条件更新 reservation_slot.booked_count。
7. 插入 reservation_record。
8. 提交事务。
```

如果任一步失败，事务必须回滚。

必须避免以下错误状态：

- **名额增加了，但没有预约记录。**
- **预约记录插入了，但名额没有增加。**
- **并发请求导致成功记录数超过总名额。**
- **同一身份证同一天出现多条成功预约记录。**

### 8.4 重复预约控制

重复预约由两层保证：

```text
第一层：后端业务查询，提前判断是否已有预约。
第二层：数据库唯一约束 reservation_record(id_card, visit_date) 兜底。
```

即使两个重复请求同时进入系统，数据库唯一约束也能保证最终只插入一条成功预约记录。

### 8.5 名额一致性核对

压测或功能测试完成后，需要核对：

```text
reservation_slot.booked_count = reservation_record 中对应时段 SUCCESS 记录数
reservation_slot.booked_count <= reservation_slot.total_capacity
```

核对 SQL 思路：

```sql
SELECT
    s.id AS slot_id,
    s.slot_name,
    s.total_capacity,
    s.booked_count,
    COUNT(r.id) AS success_record_count
FROM reservation_slot s
LEFT JOIN reservation_record r
    ON s.id = r.slot_id
   AND r.status = 'SUCCESS'
GROUP BY s.id, s.slot_name, s.total_capacity, s.booked_count;
```

验收标准：

```text
booked_count 必须等于 success_record_count。
booked_count 必须小于等于 total_capacity。
```

## 9. 常用统计查询设计

### 9.1 查询游客总数

```sql
SELECT COUNT(*) AS visitor_count
FROM visitor;
```

### 9.2 查询预约总数

```sql
SELECT COUNT(*) AS reservation_count
FROM reservation_record
WHERE status = 'SUCCESS';
```

### 9.3 查询各日期预约统计

```sql
SELECT
    visit_date,
    COUNT(*) AS reservation_count
FROM reservation_record
WHERE status = 'SUCCESS'
GROUP BY visit_date
ORDER BY visit_date;
```

### 9.4 查询各时段预约统计

```sql
SELECT
    s.visit_date,
    s.slot_name,
    s.total_capacity,
    s.booked_count,
    s.total_capacity - s.booked_count AS remaining_count
FROM reservation_slot s
ORDER BY s.visit_date, s.start_time;
```

### 9.5 查询后台预约名单

```sql
SELECT
    r.reservation_no,
    v.name,
    r.id_card,
    r.phone,
    r.visit_date,
    r.slot_name,
    r.created_at
FROM reservation_record r
JOIN visitor v ON r.visitor_id = v.id
WHERE r.status = 'SUCCESS'
ORDER BY r.created_at DESC;
```

### 9.6 查询我的预约记录

```sql
SELECT
    reservation_no,
    visit_date,
    slot_name,
    status,
    qr_content,
    created_at
FROM reservation_record
WHERE id_card = ?
  AND phone = ?
ORDER BY created_at DESC;
```
