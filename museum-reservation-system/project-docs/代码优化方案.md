# 博物馆预约系统——代码优化方案

> 基于性能测试1~4的实测数据（优化前基线），从 **5个优化方向** 提出具体代码级措施。

---

## 一、优化前性能基线（实测数据）

| 测试项 | 关键指标 |
|--------|---------|
| 测试1: 418并发预约 | 耗时 2.82s，吞吐 148.3 req/s，成功 50，数据一致性 PASS |
| 测试2: 读接口 ab | slots 1017 req/s, museum/info 2206 req/s, notices 3067 req/s |
| 测试3: 10万条数据 | reservations/my 升至 23.79ms，其他接口基本稳定 |
| 测试4: 5000并发 | 峰值吞吐 277.9 req/s，全部成功，但 5000 并发时吞吐开始下降 |

**瓶颈分析**：

1. **每个请求同步写日志**：`RequestLogInterceptor.afterCompletion()` 每次请求都 INSERT 一行日志，高并发下与业务 SQL 争夺数据库连接
2. **预约流程 DB 操作过多**：`createReservation()` 一次预约需要 10+ 次数据库操作（查游客→锁游客→查时段→查活动→查重复→查当日次数→扣名额→插记录→回查记录）
3. **读接口每次都查数据库**：场馆信息、公告等变化极少的数据，每次请求都执行 SQL
4. **数据库连接池太小**：HikariCP 默认 `maximum-pool-size=10`，高并发时线程排队等连接
5. **Tomcat 线程池太小**：默认 `max=200`，5000 并发时处理能力不足

---

## 二、优化方向与具体措施

### 优化1：请求日志异步批量写入

**优化方向**：将同步单条 INSERT 改为异步内存队列 + 定时批量写入，消除每请求一次 DB 的开销。

**涉及文件**：
- `RequestLogInterceptor.java`
- `RequestLogRepository.java`

**当前代码问题**：
```java
// RequestLogInterceptor.java 第32行
requestLogRepository.insert(requestType, success, message);  // 每个请求都同步 INSERT
```

**具体措施**：

1. 在 `RequestLogInterceptor` 中增加一个 `LinkedBlockingQueue<LogEntry>` 内存队列（容量 10000）
2. `afterCompletion()` 只做 `queue.offer(entry)`（纯内存操作，< 1μs）
3. 新增 `@Scheduled(fixedDelay = 2000)` 定时方法 `flushLogs()`，每 2 秒把队列中的日志用 `batchUpdate` 一次性写入
4. 在 `RequestLogRepository` 中新增 `batchInsert(List<LogEntry>)` 方法，使用 `jdbcTemplate.batchUpdate()` 批量插入

**预期效果**：
- 每个请求减少 1 次 DB 操作
- 高并发时日志不再和业务请求抢连接池
- 预估吞吐量提升 10-15%

---

### 优化2：合并预约流程的数据库查询

**优化方向**：减少预约事务中的数据库往返次数，从 10 次降到 8 次。

**涉及文件**：
- `SlotRepository.java`
- `ReservationService.java`

**当前代码问题**：
```java
// ReservationService.java 第46-49行：分两步查时段和活动
AdminSlotResponse slot = slotRepository.findById(request.slotId());      // 第1次查 DB
AdminActivityResponse activity = activityRepository.findById(slot.activityId());  // 第2次查 DB

// ReservationService.java 第76行：插入记录后又回查一次
ReservationRecord record = reservationRecordRepository.findById(reservationId);  // 多余的回查
```

**具体措施**：

**措施A** — 合并时段 + 活动为一条 JOIN 查询：
```java
// SlotRepository.java 新增方法
public Optional<SlotWithActivity> findSlotWithActivity(Long slotId) {
    String sql = """
        SELECT s.id, s.activity_id, s.visit_date, s.slot_name, s.start_time, s.end_time,
               s.total_capacity, s.booked_count, s.enabled, s.version,
               a.status AS activity_status, a.booking_start, a.booking_end, a.person_limit
        FROM reservation_slot s
        INNER JOIN reservation_activity a ON s.activity_id = a.id
        WHERE s.id = ?
        """;
    return Optional.ofNullable(jdbcTemplate.queryForObject(sql, slotWithActivityMapper, slotId));
}
```

**措施B** — 去掉 INSERT 后的回查：
```java
// 优化前：insert 后还要 findById
Long id = reservationRecordRepository.insert(...);
ReservationRecord record = reservationRecordRepository.findById(id);  // ← 删掉

// 优化后：直接用已有数据构造返回对象
Long id = reservationRecordRepository.insert(...);
return new ReservationCreateResponse(id, reservationNo, request.name(), normalizedIdCard,
    request.phone(), slot.visitDate(), slot.slotName(), slot.startTime(), slot.endTime(),
    qrContent, LocalDateTime.now());
```

**预期效果**：
- 每个预约请求减少 2 次 DB 往返
- 事务持续时间缩短，锁持有时间减少
- 预估并发吞吐量提升 15-20%

### 优化3：读接口加内存缓存

**优化方向**：对变化极少的数据（场馆信息、公告列表）使用内存缓存，避免每次请求都查 DB。

**涉及文件**：
- `MuseumService.java`（或对应的 Service 类）

**具体措施**：

| 接口 | 缓存策略 | 过期时间 | 理由 |
|------|---------|---------|------|
| `GET /api/museum/info` | `volatile` 字段缓存 | 5 分钟 | 场馆信息极少变化 |
| `GET /api/notices` | `volatile` 字段缓存 | 2 分钟 | 公告变化频率低 |
| `GET /api/slots` | `volatile` 字段缓存 | 3 秒 | booked_count 实时变化，需要短缓存 |

**实现方式**（以场馆信息为例）：
```java
private volatile MuseumInfoResponse cachedMuseumInfo;
private volatile long museumInfoExpireTime = 0;

public MuseumInfoResponse getMuseumInfo() {
    long now = System.currentTimeMillis();
    if (cachedMuseumInfo != null && now < museumInfoExpireTime) {
        return cachedMuseumInfo;  // 命中缓存，0 次 DB 操作
    }
    MuseumInfoResponse info = queryMuseumInfoFromDb();
    cachedMuseumInfo = info;
    museumInfoExpireTime = now + 5 * 60 * 1000;  // 5 分钟过期
    return info;
}
```

> 使用 `volatile` 保证多线程可见性，不需要加锁（最坏情况是多个线程同时查一次 DB，结果一样）。

**预期效果**：
- 读接口命中缓存时 0 次 DB 操作，响应时间从 10-90ms → < 1ms
- 吞吐量预估提升 2-5 倍（museum/info 从 2206 → 可能 10000+ req/s）

---

### 优化4：HikariCP 数据库连接池调优

**优化方向**：增大连接池容量，减少高并发时等待连接的排队时间。

**涉及文件**：
- `application.yml`

**当前状态**：使用 HikariCP 默认配置（`maximum-pool-size=10`）。

**具体措施**：

在 `application.yml` 的 `spring.datasource` 下添加：

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 50          # 默认10 → 50（匹配 Tomcat 线程数）
      minimum-idle: 10               # 最小空闲连接
      connection-timeout: 5000       # 获取连接超时 5s（默认30s太长）
      idle-timeout: 300000           # 空闲连接5分钟后释放
      max-lifetime: 600000           # 连接最大存活10分钟
      leak-detection-threshold: 30000 # 连接泄漏检测阈值30s
```

**参数选择理由**：
- `maximum-pool-size=50`：测试4显示 2000 并发时吞吐量达到峰值，50 个连接可以支撑约 500 个并发事务（每个事务平均持有连接 ~100ms）
- `connection-timeout=5000`：快速失败比等 30 秒超时更好，用户能更快收到反馈
- `leak-detection-threshold=30000`：帮助发现未释放的连接

**预期效果**：
- 高并发时消除连接排队瓶颈
- 配合优化1（日志异步化），连接竞争大幅减少
- 预估 2000+ 并发场景吞吐量提升 20-30%

---

### 优化5：Tomcat 线程池调优

**优化方向**：增大 Tomcat 工作线程数和最大连接数，提升并发处理能力。

**涉及文件**：
- `application.yml`

**当前状态**：Tomcat 默认配置（`max=200`，`max-connections=8192`）。

**具体措施**：

在 `application.yml` 添加：

```yaml
server:
  tomcat:
    threads:
      max: 500              # 默认200 → 500
      min-spare: 50          # 最小空闲线程（默认10）
    max-connections: 10000   # 默认8192 → 10000
    accept-count: 200        # 等待队列长度
```

**参数选择理由**：
- `max=500`：测试4中 5000 并发时吞吐量开始下降，说明 200 线程不够用；500 线程配合 50 个 DB 连接，可以让更多请求并行处理
- `min-spare=50`：预热足够多的线程，避免突发流量时临时创建线程的延迟
- `max-connections=10000`：支撑 5000+ 并发连接
- `accept-count=200`：超出 max-connections 后的等待队列，避免立即拒绝

**预期效果**：
- 系统并发处理能力从 200 提升到 500
- 5000 并发时吞吐量预估从 275.4 → 400+ req/s

## 三、优化优先级排序

按预期收益排序，建议按以下顺序实施：

| 优先级 | 优化项 | 预期收益 | 实施难度 | 风险 |
|--------|--------|---------|---------|------|
| 1 | 优化3：读接口缓存 | 读接口吞吐量 ↑200-500% | 低 | 缓存过期前数据不实时 |
| 2 | 优化1：日志异步化 | 全接口吞吐量 ↑10-15% | 中 | 队列满时日志丢失 |
| 3 | 优化4：连接池调优 | 高并发吞吐 ↑20-30% | 低 | 占用更多 DB 连接 |
| 4 | 优化2：合并 DB 查询 | 预约接口吞吐 ↑15-20% | 中 | 需新增 DTO 和 SQL |
| 5 | 优化5：线程池调优 | 并发上限 200→500 | 低 | 占用更多内存 |

> 优化3和优化4只需改配置，风险最低、见效最快，建议优先实施。

## 四、优化后验证方法

实施全部 5 项优化后，重新运行测试 1~4（参考《性能测试操作教程.md》），对比优化前后数据：

1. **测试1**：观察吞吐量是否从 148.3 req/s 提升，数据一致性是否仍然 PASS
2. **测试2**：观察读接口吞吐量是否大幅提升（预估 museum/info 可达 5000+ req/s）
3. **测试3**：观察 10 万条记录时响应时间是否下降
4. **测试4**：观察 5000 并发时吞吐量是否从 275.4 提升，以及是否能支撑更高并发

**验证要点**：
- 所有测试数据一致性必须仍为 PASS（booked_count = 记录数 = 不同身份证数）
- 不能为了提升性能而牺牲数据安全

## 五、注意事项

1. **缓存一致性**：优化3的内存缓存在管理后台修改场馆信息/公告后，最多需要等待缓存过期才能看到最新数据。如果管理端修改频繁，可以在修改方法中手动清除缓存。
2. **日志完整性**：优化1的异步日志在 JVM 意外退出时，队列中未刷盘的日志会丢失。对于课程作业场景，这是可以接受的。
3. **连接池大小**：优化4的 50 个连接需要 MySQL 的 `max_connections` 足够大（默认 151，足够）。
4. **内存占用**：优化5的 500 线程约多占用 500MB 栈内存（每线程默认 1MB）。确保虚拟机内存 ≥ 4GB。
