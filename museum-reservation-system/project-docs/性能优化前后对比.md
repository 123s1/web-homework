# 博物馆预约系统 — 性能优化前后实测对比

> 测试环境：Ubuntu 22.04（VM，固定内存 8GB）+ JDK 21 + MySQL 8.0，后端以可执行 JAR 部署运行，端口 8080。
> 压测工具：ApacheBench (ab) + `scripts/perf/concurrency_test.sh`。
> 优化方向、具体措施详见 `代码优化方案.md`（本目录），本文只记录**实测的优化效果**。

---

## 一、优化项一览（3 项）

| 优化项 | 优化方向 | 核心措施 | 涉及文件 |
|--------|---------|---------|---------|
| 优化1 | 请求日志异步化 | 同步单条 INSERT → 内存队列 `LinkedBlockingQueue` + `@Scheduled` 每 2 秒 `batchUpdate` 批量落库 | `RequestLogInterceptor.java`、`RequestLogRepository.java`、`MuseumReservationApplication.java` |
| 优化2 | 合并预约流程 DB 查询 | slot 与 activity 合并为一次 JOIN 查询；去掉 INSERT 后多余的 `findById` 回查，直接用已有数据构造返回对象 | `SlotRepository.java`、`SlotWithActivity.java`、`ReservationService.java` |
| 优化3 | 读接口内存缓存 | 对变化极少的数据加 `volatile` 字段缓存 + TTL 过期（museum/info 5min、notices 2min、slots 全量 3s） | `MuseumService.java` |

## 二、测试1：418 并发预约（数据一致性 + 写入吞吐）

命令：`./concurrency_test.sh 1 50 418 100 http://127.0.0.1:8080`

| 指标 | 优化前 | 优化后 | 变化 |
|------|--------|--------|------|
| 总耗时 (s) | 2.82 | 2.46 | ↓ |
| 吞吐量 (req/s) | 148.2 | 169.9 ~ 220.9（代表值 ~205） | **↑ 约 15%~40%** |
| HTTP 200 成功数 | 50 | 50 | 一致 |
| DB booked_count | 50 | 50 | 一致 |
| 数据一致性 | PASS（无超额、无重复） | PASS（无超额、无重复） | 保持 |

> 优化后多次运行吞吐稳定高于基线；并发安全（成功数 = booked_count = 记录数 = 不同身份证）始终 PASS，未为提升性能牺牲数据安全。

## 四、测试3：大数据量查询性能（ab -n 1000 -c 50，平均响应 ms）

数据从 0 → 1千 → 1万 → 5万 → 10万条逐档累积灌入（`insert_test_data` 存储过程），观察查询接口是否随数据量增大而变慢。

**优化前**

| 接口 avg(ms) | 0条 | 1千 | 1万 | 5万 | 10万 |
|---|---|---|---|---|---|
| GET /api/slots | 92.46 | 50.74 | 30.75 | 22.58 | 28.95 |
| GET /api/museum/info | 53.70 | 35.39 | 17.33 | 14.14 | 13.50 |
| GET /api/notices | 50.10 | 33.70 | 17.87 | 12.43 | 15.66 |
| GET /api/reservations/my | 50.94 | 34.44 | 17.31 | 14.81 | 27.13 |

**优化后**

| 接口 avg(ms) | 0条 | 1千 | 1万 | 5万 | 10万 |
|---|---|---|---|---|---|
| GET /api/slots | 27.54 | 20.38 | 18.14 | 16.83 | 20.76 |
| GET /api/museum/info | 16.94 | 17.49 | 10.29 | 11.43 | 15.67 |
| GET /api/notices | 15.29 | 17.88 | 10.14 | 10.58 | 11.14 |
| GET /api/reservations/my | 15.98 | 17.74 | 11.14 | 21.94 | 15.74 |

**结论**：优化前后，读接口响应时间随数据量从 0 增长到 10 万条均保持稳定（无明显劣化，得益于命中索引）；优化后各接口平均响应整体更低。

> 说明：每组测试均为各自版本的进程冷启动，0条/1千档受 JVM 预热（JIT、连接池冷启）影响数值偏高，属正常现象；横向对比应重点看“数据量增大后是否稳定”，结论是两版本都稳定。

## 五、测试4：并发极限阶梯（名额 10000，并发 100→500→1000→2000→5000）

每轮前重置 `total_capacity=10000, booked_count=0` 并清空记录，统计写路径（预约下单）吞吐与数据一致性。

| 并发数 | 优化前 吞吐(req/s) | 优化后 吞吐(req/s) | 成功数(前/后) | 数据一致性 |
|---|---|---|---|---|
| 100 | 87.7 | 198.1 | 100 / 100 | PASS |
| 500 | 128.2 | 193.5 | 500 / 500 | PASS |
| 1,000 | 228.0 | 201.6 | 1000 / 1000 | PASS |
| 2,000 | 273.1 | 283.6 | 2000 / 2000 | PASS |
| 5,000 | 280.6 | 289.9 | 5000 / 5000 | PASS |

> 每轮 `booked_count = 记录数 = 不同身份证数 = 成功数`，全程无超额、无重复、无失败。

**结论**：
- **数据安全**：优化前后在 5000 并发下均 100% 成功且数据完全一致，未因优化牺牲并发安全。
- **吞吐特征**：中低并发（100/500）优化后提升明显；高并发（2000/5000）两版本吞吐趋于接近。原因是预约下单对**同一个时段行**做原子 `UPDATE booked_count`，单行锁天然串行化，高并发下吞吐受该行锁瓶颈主导而趋于饱和——这是“并发安全”设计的固有代价，与优化项无关。
- 写路径优化（合并查询 + 去回查 + 日志异步化）主要降低了**单次请求的 DB 往返与延迟**，在锁竞争未饱和时（中低并发）收益更直观。

---

## 六、结论

- **写路径**（预约下单）：合并 DB 查询 + 去回查 + 日志异步化，中低并发吞吐提升明显；高并发受单行锁主导趋于饱和，数据一致性始终 PASS。
- **读路径**（场馆信息/公告/时段）：内存缓存使吞吐提升 2.3~2.8 倍，平均响应时间下降约 60%~65%；大数据量（10万条）下响应保持稳定。
- 全程无 5xx、无连接错误，并发一致性测试（测试1、测试4）全部 PASS。

### 注意事项

1. **缓存一致性**：读接口为 TTL 缓存，管理端修改场馆信息/公告后，最长需等待 TTL（5min / 2min）才能看到最新数据。
2. **日志完整性**：异步日志在 JVM 异常退出时，队列中未刷盘的日志可能丢失（已加 `@PreDestroy` 在正常关闭时尽量刷盘）；对统计型日志可接受。
