# 博物馆预约系统 — 性能优化前后实测对比

> 测试环境：Ubuntu 22.04（VM，固定内存 8GB）+ JDK 21 + MySQL 8.0，后端以可执行 JAR 部署运行，端口 8080。
> 压测工具：ApacheBench (ab) + `scripts/perf/concurrency_test.sh`。
> 优化方向、具体措施详见 `代码优化方案.md`（本目录），本文只记录**实测的优化效果**。

---

## 一、优化项一览（3 项）

| 优化项 | 优化方向 | 核心措施 | 涉及文件 |
|--------|---------|---------|---------|
| 优化1 | 请求日志异步化 | 同步单条 INSERT → 内存队列 `LinkedBlockingQueue` + `@Scheduled` 每 2 秒 `batchUpdate` 批量落库 | `RequestLogInterceptor.java`、`RequestLogRepository.java`、`MuseumReservationApplication.java` |
| 优化2 | 合并预约流程 DB 查询 | slot 与 activity 合并为一次 JOIN 查询；去掉 INSERT 后多余的 `findById` 回查，直接用已有数据构造返回对象 | `SlotRepository.java`、`SlotWithActivity.java`、`ReservationService.java` |
| 优化3 | 读接口内存缓存 | 对变化极少的数据加 `volatile` 字段缓存 + TTL 过期（museum/info 5min、notices 2min、slots 全量 3s） | `MuseumService.java` |

---

## 二、测试1：418 并发预约（数据一致性 + 写入吞吐）

命令：`./concurrency_test.sh 1 50 418 100 http://127.0.0.1:8080`

| 指标 | 优化前 | 优化后 | 变化 |
|------|--------|--------|------|
| 总耗时 (s) | 2.82 | 2.46 | ↓ |
| 吞吐量 (req/s) | 148.2 | 169.9 ~ 220.9（代表值 ~205） | **↑ 约 15%~40%** |
| HTTP 200 成功数 | 50 | 50 | 一致 |
| DB booked_count | 50 | 50 | 一致 |
| 数据一致性 | PASS（无超额、无重复） | PASS（无超额、无重复） | 保持 |

> 优化后多次运行吞吐稳定高于基线；并发安全（成功数 = booked_count = 记录数 = 不同身份证）始终 PASS，未为提升性能牺牲数据安全。

## 三、测试2：读接口高并发（ab -n 5000 -c 100）

| 接口 | 优化前 吞吐 (req/s) | 优化后 吞吐 (req/s) | 提升倍数 | 优化前 平均响应 (ms) | 优化后 平均响应 (ms) |
|------|------|------|------|------|------|
| GET /api/slots | 1010.61 | 2874.52 | **2.84×** | 98.95 | 34.79 |
| GET /api/museum/info | 2425.80 | 6512.06 | **2.68×** | 41.22 | 15.36 |
| GET /api/notices | 2693.34 | 6174.62 | **2.29×** | 37.13 | 16.20 |

> 三个读接口 `Failed requests` 均为 0。命中缓存后请求不再访问数据库，吞吐量整体提升约 130%~184%。

---

## 四、结论

- **写路径**（预约下单）：合并 DB 查询 + 去回查 + 日志异步化，吞吐稳定提升，数据一致性保持 PASS。
- **读路径**（场馆信息/公告/时段）：内存缓存使吞吐提升 2.3~2.8 倍，平均响应时间下降约 60%~65%。
- 全程无 5xx、无连接错误，并发一致性测试全部 PASS。

### 注意事项

1. **缓存一致性**：读接口为 TTL 缓存，管理端修改场馆信息/公告后，最长需等待 TTL（5min / 2min）才能看到最新数据。
2. **日志完整性**：异步日志在 JVM 异常退出时，队列中未刷盘的日志可能丢失（已加 `@PreDestroy` 在正常关闭时尽量刷盘）；对统计型日志可接受。
