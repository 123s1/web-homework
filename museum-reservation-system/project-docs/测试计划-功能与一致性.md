# 测试计划 · 功能 + 并发一致性（在本机 Linux 部署上执行）

被测环境：本机 Ubuntu 22.04，按 `deploy/` 脚本部署（Nginx:80 → Spring Boot:8080 → MySQL8）。
管理员账号：admin / admin123（schema 初始数据）。

被测变更重点：
1. 并发缺陷修复 —— 全新身份证首次并发预约不再返回 500（`ReservationService.getOrCreateVisitor` 捕获 `DuplicateKeyException` 重查）。
2. 部署可用性 —— 经 Nginx 访问前端 + `/api` 反代后端，核心业务可跑通。

## A. 游客预约主流程（黄金路径）

| # | 操作 | 预期（具体判据） |
|---|---|---|
| A1 | 浏览器打开 `http://127.0.0.1/` | 首页加载，显示博物馆名称「省博物馆」、开放信息/须知、公告区;无报错 |
| A2 | 进入「在线预约 / 我要预约」→ 游客登录页 `/visitor/login`，填姓名+身份证(18位合法)+手机号，提交 | 登录成功，进入时段列表 `/slots` |
| A3 | 在 `/slots` 选择一个「剩余>0、状态开放」的时段，点击预约 | 跳转预约结果页 `/reservation/result`，显示预约号、姓名、日期、时段、**二维码图片可见** |
| A4 | 进入「我的预约」`/reservations/my`（按身份证查询） | 列表出现刚才的预约记录，状态为已预约/有效，可见二维码入口 |

## B. 业务规则拦截（不超额/不重复/格式校验）—— 若变更被破坏会表现不同

| # | 操作 | 预期（具体判据） |
|---|---|---|
| B1 | 用**同一身份证**对**同一时段**再次提交预约 | 提交被拒，提示文案包含「已预约过该时段」;不产生第二条记录 |
| B2 | 选择一个已约满（剩余=0）的时段提交 | 提交被拒，提示文案包含「名额已满」;`booked_count` 不超过 `total_capacity` |
| B3 | 游客登录填入非法身份证（如 `12345`）提交 | 前端/后端校验拦截，提示「身份证号格式不正确」，不发起成功预约 |

## C. 管理员后台

| # | 操作 | 预期（具体判据） |
|---|---|---|
| C1 | 打开 `/admin/login`，输入 admin/admin123 登录 | 进入后台首页 `/admin`，显示统计/概览 |
| C2 | 打开「预约活动」`/admin/activities` 与「时段管理」`/admin/slots` | 能看到活动与各时段的名额/已约/剩余;数据与前台一致 |
| C3 | 打开「预约名单」`/admin/reservations`，查看记录并点击「导出 CSV」 | 列表含 A 步骤产生的预约;点击导出后浏览器下载到 `.csv` 文件 |
| C4 | 打开「系统状态」`/admin/status` | 显示系统/数据库状态(UP)、请求量等运行指标 |

## D. 并发一致性（命令行证据，纳入性能测试报告）

| # | 操作 | 预期 |
|---|---|---|
| D1 | `scripts/perf/concurrency_test.sh 9001 50 1000 200` | 成功数=booked_count=记录数=50;断言 PASS（不超额） |
| D2 | 同一身份证并发 100 次抢同一时段 | 仅 1 次 200，其余 400;**无 500**（修复验证） |

> D 已在本会话用 shell 执行通过（详见 `性能测试报告.md`）。本计划的 UI 录制聚焦 A/B/C。

## 判据为何能区分"坏实现"
- B1/B2 若并发/唯一约束或条件更新被破坏，会出现重复记录或超额（数值可见不同）。
- 修复点 D2：未修复时同一新身份证并发会出现 500;修复后只有 400。
- A3 二维码若后端未生成 qrContent 或前端未渲染，结果页将无二维码。
