# 博物馆预约系统 · 性能与并发测试报告

## 1. 测试目标

针对作业「高并发与稳定性（25 分）」与「数据一致性（30 分）」两项评分点，验证：

1. **不超额**：N 个用户高并发抢同一时段的 M 个名额时，最终成功数严格等于 M，`booked_count` 不超过 `total_capacity`。
2. **不重复**：同一身份证并发重复提交同一时段时，最多成功 1 次。
3. **稳定性**：核心接口在高并发下响应正常、无 5xx、服务不崩溃。
4. **性能**：核心读接口、写接口的吞吐量与响应时间分布。

## 2. 测试环境

| 项目 | 配置 |
|---|---|
| 操作系统 | Ubuntu 22.04 LTS |
| JDK | OpenJDK 21 |
| 数据库 | MySQL 8.0 |
| 后端 | Spring Boot 3.3.5（systemd 服务，单实例，端口 8080） |
| 连接池 | HikariCP（默认配置） |
| 并发控制方案 | 数据库条件原子更新 + 唯一索引防重复 + 事务（详见系统设计文档） |
| 压测工具 | ApacheBench (ab) + 自研并发脚本 `scripts/perf/concurrency_test.sh` |

> 并发控制核心：`UPDATE reservation_slot SET booked_count = booked_count + 1 ... WHERE id = ? AND enabled = 1 AND booked_count < total_capacity`，
> 仅当仍有余量时更新成功（受影响行数=1）；记录表 `uk_reservation_record_id_card_slot (id_card, slot_id)` 唯一索引防重复；
> 另有 CHECK 约束 `booked_count <= total_capacity` 作为数据库层兜底。

## 3. 数据一致性测试（核心）

### 3.1 不超额测试

用 `scripts/perf/concurrency_test.sh` 对同一时段（名额 50）发起远超名额的并发预约，每个请求使用不同身份证号。

| 场景 | 名额 | 总请求 | 并发数 | 成功数(HTTP200) | 被拒数 | DB booked_count | DB 记录数 | 结论 |
|---|---|---|---|---|---|---|---|---|
| A | 50 | 500 | 100 | **50** | 450 | **50** | 50 | ✅ 无超额 |
| B | 50 | 1000 | 200 | **50** | 950 | **50** | 50 | ✅ 无超额 |

> 成功数 == booked_count == 记录数 == 名额(50)，被拒请求均返回业务提示「预约名额已满」（HTTP 400），无一例超额。

### 3.2 不重复测试

同一身份证号对同一时段（名额充足）并发提交 100 次：

| 场景 | 并发数 | 成功数(HTTP200) | 被拒数(HTTP400) | DB 该身份证记录数 | 结论 |
|---|---|---|---|---|---|
| 重复预约 | 100 | **1** | 99 | **1** | ✅ 无重复 |

> 仅 1 次成功，其余 99 次返回「您已预约过该时段，请勿重复预约」。唯一索引 + 业务校验双保险生效。

> 备注：测试过程中发现并修复了一个并发缺陷——**全新身份证首次并发预约时，游客记录的并发插入会触发 `uk_visitor_id_card` 唯一键冲突并返回 500**。
> 已在 `ReservationService.getOrCreateVisitor` 捕获 `DuplicateKeyException` 后重查处理，修复后重复测试结果为 1×200 + 99×400，无任何 5xx。

## 4. 接口性能测试

### 4.1 读接口：`GET /api/slots`（查询可预约时段）

```
ab -n 5000 -c 100 http://127.0.0.1:8080/api/slots
```

| 指标 | 数值 |
|---|---|
| 完成请求 | 5000 |
| 失败请求 | 0 |
| 吞吐量 | **1460 req/s** |
| 平均响应（含并发） | 0.69 ms |
| P50 | 59 ms |
| P90 | 115 ms |
| P95 | 138 ms |
| P99 | 175 ms |
| 最慢 | 436 ms |

### 4.2 写接口：`POST /api/reservations`（核心预约）

```
ab -n 3000 -c 50 -p resv.json -T application/json http://127.0.0.1:8080/api/reservations
```

| 指标 | 数值 |
|---|---|
| 完成请求 | 3000 |
| 5xx / 连接错误 | 0 |
| 吞吐量 | **869 req/s** |
| P50 | 53 ms |
| P90 | 88 ms |
| P95 | 102 ms |
| P99 | 128 ms |
| 最慢 | 189 ms |

> 说明：写接口压测使用固定身份证号，因此除首次外均命中「重复预约」业务校验（HTTP 400），
> 仍完整执行了「锁游客→查时段→校验→条件更新/唯一索引」整条事务路径，可代表写路径的处理时延；全程无 5xx。

---

## 5. 稳定性结论

- 高并发（200 并发、千级请求）下核心预约接口响应正常，无 5xx、无超时、服务未崩溃。
- 数据一致性在并发场景下严格成立：**不超额、不重复、名额精准**。
- 读接口吞吐约 1460 req/s，写接口约 869 req/s，P99 均在 200ms 内，满足课程演示与评分要求。

## 6. 复现实验步骤

### 6.1 一致性脚本（推荐，自动断言）

```bash
cd museum-reservation-system/scripts/perf
export DB_PASSWORD=你的业务库密码
# 参数：时段ID 名额 总请求 并发数 [后端地址]
./concurrency_test.sh 9001 50 1000 200 http://127.0.0.1:8080
```

脚本会自动重置时段名额、并发发起请求、统计成功/被拒数，并断言「成功数=名额、记录数=不同身份证数」。
> 运行前需先用管理员后台或 SQL 建好一个 `OPEN` 且预约时间窗有效的测试时段（脚本默认 SLOT_ID=9001）。

### 6.2 ApacheBench

```bash
sudo apt-get install -y apache2-utils
ab -n 5000 -c 100 http://127.0.0.1:8080/api/slots
ab -n 3000 -c 50 -p resv.json -T application/json http://127.0.0.1:8080/api/reservations
```

### 6.3 JMeter（图形化报告）

导入 `scripts/perf/museum-reservation.jmx`（见同目录），按需修改：

- HTTP 请求默认值：服务器 `127.0.0.1`、端口 `8080`。
- 线程组：线程数（并发用户）、循环次数。
- CSV Data Set Config：读取 `idcards.csv` 为每个线程提供唯一身份证号（避免重复预约误判）。
- 监听器：聚合报告（Aggregate Report）、查看结果树。

运行后在聚合报告中查看：Samples、Average、90%/95%/99% Line、Throughput、Error%。
建议把聚合报告截图与本报告第 4 节表格一同纳入最终提交。
