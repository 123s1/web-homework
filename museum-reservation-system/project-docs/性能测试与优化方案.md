## 〇、完整操作步骤（虚拟机中执行）

> 以下是在虚拟机中从头到尾执行性能测试和优化的全部步骤。每个步骤开头都有**环境检查**，已具备的直接跳过。
>
> **注意**：文档中的命令分两种：
> - **`bash` 代码块** → 在虚拟机**终端**（Terminal）中执行
> - **`sql` 代码块** → 需要先连接 MySQL，再执行 SQL 语句
>
> **连接 MySQL 的方法**（二选一）：
> - 方法A：进入 MySQL 交互界面 → `mysql -u root -p museum_reservation`，输入密码后，在 `mysql>` 提示符下输入 SQL
> - 方法B：不进交互界面，直接在终端一行执行 → `mysql -u root -p museum_reservation -e "这里写SQL语句"`
>
> 如果你的数据库用户名不是 root，换成你实际的用户名。

## 一、项目概况

```
项目名称：省博物馆预约系统
技术栈：  Spring Boot 3.3.5 + JDK 21 + MySQL 8.0 + Vue 3
后端入口：MuseumReservationApplication.java
端口：    8080（application.yml → server.port: 8080）
数据库：  museum_reservation（application.yml → spring.datasource）
构建工具：Maven Wrapper（./mvnw）
```

### 1.1 数据库表结构（schema.sql）

| 表名 | 用途 | 关键索引 |
|------|------|---------|
| `admin_user` | 管理员账号 | UNIQUE(username) |
| `visitor` | 游客信息 | UNIQUE(id_card) |
| `museum_info` | 场馆信息（1条） | idx_status |
| `notice` | 公告（3条） | idx_enabled, idx_created_at |
| `reservation_activity` | 预约活动（3个活动，对应未来3天） | UNIQUE(visit_date) |
| `reservation_slot` | 时段（12个，每天4场，每场50人） | idx_visit_date_enabled, version字段 |
| `reservation_record` | 预约记录 | UNIQUE(id_card, slot_id), idx_slot_status |
| `request_log` | 请求日志（每个API请求写1条） | idx_request_type, idx_created_at |

### 1.2 核心 API 接口

| 接口 | Controller | 类型 | 说明 |
|------|-----------|------|------|
| `POST /api/reservations` | ReservationController | 写 | **核心——创建预约**，高并发关键路径 |
| `GET /api/reservations/my?idCard=xxx` | ReservationController | 读 | 查询我的预约 |
| `GET /api/slots` | MuseumController | 读 | 查询可用时段（JOIN reservation_activity） |
| `GET /api/museum/info` | MuseumController | 读 | 查场馆信息（1条记录） |
| `GET /api/notices` | MuseumController | 读 | 查公告列表 |
| `GET /api/health` | HealthController | 读 | 健康检查 |

### 1.3 预约接口（POST /api/reservations）完整流程

```
ReservationController.createReservation()
  → ReservationService.createReservation()
    → 请求体：{"name":"张三", "idCard":"110101199001000001", "phone":"13900000001", "slotId":1}

    1. visitorRepository.findByIdCard(idCard)               → SELECT visitor
    2. visitorRepository.insert() 或 updateById()           → INSERT/UPDATE visitor
    3. visitorRepository.lockById(visitor.id)                → SELECT id FROM visitor WHERE id=? FOR UPDATE
    4. slotRepository.findById(slotId)                       → SELECT reservation_slot WHERE id=?
    5. activityRepository.findById(slot.activityId)          → SELECT reservation_activity WHERE id=?
    6. reservationRecordRepository.existsSuccessByIdCardAndSlot()  → SELECT COUNT(*) (重复预约检查)
    7. reservationRecordRepository.countSuccessByIdCardAndVisitDate() → SELECT COUNT(*) (当天次数)
    8. slotRepository.increaseBookedCount(slotId)            → UPDATE reservation_slot SET booked_count+1
                                                               WHERE id=? AND booked_count < total_capacity (乐观锁)
    9. reservationRecordRepository.insert()                  → INSERT reservation_record
   10. reservationRecordRepository.findById(reservationId)   → SELECT reservation_record WHERE id=?

    共 10 次数据库操作
```

加上 RequestLogInterceptor 的1次 INSERT request_log = **每个预约请求实际 11 次 DB 操作**。

## 二、现有代码性能瓶颈分析

### 瓶颈1：每个请求同步写日志到数据库（影响全部接口）

**位置**：`RequestLogInterceptor.java` → `afterCompletion()` → `requestLogRepository.insert()`

```java
// RequestLogInterceptor.java 第23-35行
@Override
public void afterCompletion(HttpServletRequest request, HttpServletResponse response, Object handler, Exception ex) {
    if ("OPTIONS".equalsIgnoreCase(request.getMethod())) return;
    // ...
    requestLogRepository.insert(requestType, success, message);  // ← 同步写 DB
}
```

`WebMvcConfig` 把这个拦截器注册到 `/api/**`，所以**每个API请求都多一次 INSERT INTO request_log**。

**影响**：418 并发预约 = 额外 418 次 INSERT，和预约事务争抢 HikariCP 的 10 个连接。

### 瓶颈2：单次预约 10 次 DB 操作（影响写接口）

见上面 1.3 的流程分析。其中可优化的点：

| 步骤 | 当前 | 可优化为 |
|------|------|---------|
| 4+5 | 分两条 SQL 查 slot 和 activity | 合并为 1 条 JOIN 查询 |
| 10 | INSERT 后再 SELECT 回查 | 省掉，直接用已有数据组装返回 |

**优化后**：10次 → 8次（减少 20%），加上日志异步化后从 11次 → 8次（减少 27%）。

### 瓶颈3：读接口无缓存（影响读接口）

| 接口 | 数据特点 | 当前实现 |
|------|---------|---------|
| `GET /api/museum/info` | 全局 1 条记录，极少变 | 每次 SELECT museum_info |
| `GET /api/notices` | 3条公告，偶尔更新 | 每次 SELECT notice WHERE enabled=1 |
| `GET /api/slots` | 12条时段，booked_count 变化 | 每次 SELECT ... JOIN reservation_activity |

`museum/info` 和 `notices` 完全可以缓存几分钟。

### 瓶颈4：HikariCP 连接池默认 10 个连接

`application.yml` 没有配置 `spring.datasource.hikari`，Spring Boot 默认：
- `maximum-pool-size = 10`
- `minimum-idle = 10`
- `connection-timeout = 30000ms`

当 418 并发到来时，10 个连接远远不够，大量请求排队等连接。

### 瓶颈5：Tomcat 线程池默认 200

`application.yml` 没有配置 `server.tomcat.threads`，默认：
- `max = 200`
- `min-spare = 10`

200 线程对于几千并发不够。

## 四、优化方案

根据第二章的瓶颈分析和第三章的测试数据，实施以下 5 项优化。

### 优化1：请求日志异步批量写入

**改什么**：`RequestLogInterceptor.java` + `RequestLogRepository.java`

**优化前**（当前代码）：
```java
// RequestLogInterceptor.java — afterCompletion()
requestLogRepository.insert(requestType, success, message);  // 同步 INSERT
```

**优化后**：
```java
// 1. 请求结束后只放入内存队列
private final BlockingQueue<LogEntry> queue = new LinkedBlockingQueue<>(10000);

@Override
public void afterCompletion(...) {
    queue.offer(new LogEntry(requestType, success, message));  // 不写 DB
}

// 2. 定时任务每2秒批量写入
@Scheduled(fixedDelay = 2000)
public void flushLogs() {
    List<LogEntry> batch = new ArrayList<>();
    queue.drainTo(batch, 500);
    if (!batch.isEmpty()) {
        requestLogRepository.batchInsert(batch);  // 1条SQL插入多行
    }
}
```

**RequestLogRepository 新增**：
```java
public void batchInsert(List<LogEntry> entries) {
    jdbcTemplate.batchUpdate(
        "INSERT INTO request_log (request_type, success, message) VALUES (?, ?, ?)",
        entries, entries.size(),
        (ps, entry) -> {
            ps.setString(1, entry.requestType());
            ps.setInt(2, entry.success() ? 1 : 0);
            ps.setString(3, entry.message());
        });
}
```

**效果**：每个请求减少 1 次 DB 操作（11次 → 10次），高并发下不再和业务请求抢连接。

### 优化3：读接口加内存缓存

**改什么**：`MuseumService.java`

```java
// 场馆信息——缓存5分钟（数据几乎不变）
private volatile MuseumInfoResponse cachedMuseumInfo;
private volatile long museumInfoExpireTime = 0;

public MuseumInfoResponse getMuseumInfo() {
    long now = System.currentTimeMillis();
    if (cachedMuseumInfo != null && now < museumInfoExpireTime) {
        return cachedMuseumInfo;  // 命中缓存，0次DB操作
    }
    MuseumInfoResponse info = queryMuseumInfoFromDb();  // 原来的查询逻辑
    cachedMuseumInfo = info;
    museumInfoExpireTime = now + 5 * 60 * 1000;  // 5分钟后过期
    return info;
}

// 公告列表——缓存2分钟
// 可用时段——缓存3秒（实时性要求较高，因为 booked_count 会变）
```

**效果**：读接口命中缓存时响应时间从 几ms 降到 < 1ms，吞吐量提升 2-5 倍。
